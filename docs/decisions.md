# Decisions
1. **Tailwind v3 with CSS-variable tokens** over v4: stable, simple class-based dark mode, tokens swap per theme in one place.
2. **Theme set by inline script in index.html** so there is no flash of the wrong theme.
3. **Vite dev server proxies /api to :8000**, so no CORS pain in dev.
4. **Backend has only /api/health in Stage 1.** No DB, Docker or LLM yet (Stages 2+).

## Stage 2
5. **UUID primary keys** (not auto-increment ints): IDs in URLs can't be guessed or enumerated, which backs up per-user isolation. Cost: slightly larger indexes.
6. **Repositories take `user_id` on every query.** Isolation lives in the data layer, not in each route, so a forgotten check can't leak data. Messages are checked through their parent conversation.
7. **Repository tests run on in-memory SQLite** (fast, no Docker, works in CI). Tradeoff: SQLite is not Postgres. Postgres-only features (pgvector, Stage 7+) will get tests against a real Postgres service in CI. The Alembic migration must be run once against Postgres (`alembic upgrade head`).
8. **Alembic with async engine**; URL comes from `settings.database_url`, so `alembic.ini` holds no credentials. Migration was autogenerated, then upgrade/downgrade checked on SQLite.
9. **`messages.created_at` is set in Python (microseconds)**, not DB `now()`. Root cause found by a failing test: second-resolution timestamps tied and ordering fell back to random UUIDs. `id` stays as tie-breaker.
10. **Cascade deletes at DB level** (`ON DELETE CASCADE` + `passive_deletes`): deleting a conversation or user removes children without loading them (needed later for "delete account").
11. **Role is a string with a CHECK constraint**, not a Postgres enum: enums are painful to migrate.

## Stage 3
12. **Two-token auth.** Access token = short-lived JWT (15 min, HS256) sent as `Authorization: Bearer`, kept only in JS memory. Refresh token = opaque random string (14 days) in an httpOnly, SameSite=Lax cookie scoped to `/api/auth`. Why: JS can never read the long-lived credential (XSS), while per-request checks stay stateless and cheap. Options rejected: JWT in localStorage (XSS-stealable), server sessions only (a DB hit on every request).
13. **Refresh tokens are opaque and stored as SHA-256 hashes** in `refresh_tokens` (not JWTs), so they can be revoked: logout works for real and a DB leak doesn't expose usable tokens.
14. **Rotation, single use.** `refresh` revokes the old token and issues a new pair, via one `UPDATE ... RETURNING` so two concurrent requests can't both succeed. The frontend shares one in-flight refresh call for the same reason.
15. **Argon2id** (argon2-cffi) for passwords: memory-hard, current OWASP recommendation. Login returns the same 401 for unknown email and wrong password, and burns a dummy hash so timing doesn't reveal which emails exist.
16. **CSRF:** the access token is a header (not a cookie), so normal API calls aren't CSRF-able. Only `refresh`/`logout` use the cookie; they are POST-only and the cookie is SameSite=Lax.
17. **404 (not 403) for other users' conversations**, so IDs can't be probed.
18. **Register returns 409 for a taken email.** Friendlier, but reveals the email exists. Accepted for now; login/register rate limiting arrives in Stage 10.
19. **Added minimal `GET/POST /api/conversations` and `GET /api/conversations/{id}`** (early, on purpose) so isolation can be tested through the HTTP API. Everything else on conversations stays in Stage 4.
20. **`JWT_SECRET` has no default**: the app refuses to start without a 32+ char secret.

## Stage 4
21. **`LLMProvider` ABC with `stream_chat` (+ derived `complete`)**. Vendors differ only inside `llm/gemini.py`, `llm/ollama.py`; the chat service never imports them. `FakeLLMProvider` is the default so the app and CI run with no key and no cost. Embeddings join the interface in Stage 7, when something uses them.
22. **Raw `httpx` instead of vendor SDKs**: one dependency we already have, streaming is easy to unit-test with `httpx.MockTransport`, and we control retries.
23. **SSE over WebSockets**: chat is one-way (server to client) per request, works over plain HTTP, and Stop is just aborting the fetch. Events: `token`, `done` (message id + optional title), `error` (code, friendly message, retryable).
24. **No DB connection held while streaming.** The route prepares a "turn" using short sessions, streams with none open, then saves the reply in a new session. `get_current_user` also commits after loading the user so its connection returns to the pool. Why: an LLM call can take 30s+, and a pool of ~15 connections would otherwise cap you at ~15 concurrent chats.
25. **Stop keeps the partial reply**: on disconnect/cancel the generator saves what had streamed, via `asyncio.shield` so the save survives cancellation. Same path covers a mid-stream model error.
26. **Retry and regenerate are one endpoint** (`POST .../messages/{mid}/regenerate`): if the last message is an assistant reply it is replaced; if it is a user message (the reply failed) it just generates. Only the newest message is allowed (409 otherwise), so history can't be rewritten in the middle. The frontend re-reads the latest id before calling, because a stopped reply's id is only known to the server.
27. **Retries on 429/503 with exponential backoff + jitter, only before the first token** is sent, so the user never sees duplicated text. After the last retry: `model_busy`.
28. **Auto title = one extra LLM call** on the first exchange only, with a local fallback (first 40 chars) if it fails. Costs 1 extra free-tier request per new conversation.
29. **Bounded context**: last 20 messages, 8,000-char messages, 800 output tokens (all configurable). Per-user daily budgets and throttling are Stage 10.
30. **Users see friendly errors only**; provider details go to server logs. Gemini key travels in a header, never the URL.
31. **Bug found by tests**: after PATCH, `updated_at` (DB-side `onupdate`) was expired, so serializing it hit a lazy load and crashed. Fixed by refreshing the row in the repository.

## Stage 5
32. **`MemoryProvider` interface** (`search`, `add_exchange`) so Mem0 now and our own implementation in Stage 7 are swappable and comparable. Listing/editing is added in Stage 6 when something needs it.
33. **Mem0 runs fully free and local**: Gemini/Ollama for extraction, `fastembed` (384-dim) for embeddings, our Postgres+pgvector for vectors, Mem0 telemetry disabled. Mem0 is an optional install (`requirements-mem0.txt`) because it is heavy.
34. **The server enforces the memory switch**, read from the database at turn start. When off, the memory provider is never called for that conversation (tested by call counters). The background write re-checks the switch right before writing, so turning it off mid-reply still prevents the write.
35. **Memory never breaks chat**: search has a timeout (8s) and any failure means "answer without memory". Writes are fire-and-forget background tasks so the reply isn't delayed; failures are logged.
36. **Only new exchanges are remembered.** Regenerating a reply isn't a new exchange; retrying after a failed first attempt is. Stopped replies aren't remembered (incomplete).
37. **Memories enter the prompt as labelled data**, newlines flattened and capped at 300 chars each. A stored memory is user-influenced text, so it is a prompt-injection path; this reduces, not eliminates, the risk.
38. **`messages.memories_used` is a JSON snapshot** (id, text, score), not a foreign key: the user still sees what influenced a reply after the memory is edited or deleted. The chip shows a count; the list is fetched on click.
39. **Cost reality**: each remembered exchange makes Mem0 call the LLM on its own (extraction, possibly a second call to decide updates). That is extra free-tier usage per message, and exactly the number to compare against our own batched extractor in Stage 9.
40. **Migration 0003** adds the JSON column and `CREATE EXTENSION IF NOT EXISTS vector` (Postgres only).

## Stage 6
41. **`MemoryProvider` gains `list_all`, `get`, `update`, `delete`, `delete_all`**, all taking `user_id`. Mem0's own get/update/delete accept only a memory id, so the Mem0 adapter fetches the memory and checks its `user_id` before every change (tested: another user's id is never mutated). The Fake does the same by construction.
42. **404, not 403, for someone else's memory** (same reasoning as conversations).
43. **Deleting a memory also deletes its text from `messages.memories_used` snapshots.** Stage 5 kept snapshots so history survives edits; but a user who deletes a memory expects it gone everywhere we copied it. Editing leaves old snapshots alone: they record what was used at the time.
44. **"Delete all" is guarded twice**: the UI asks the user to type DELETE, and the endpoint (`POST /api/memories/delete-all`, a POST so the body isn't dropped) rejects anything but `{"confirm": "DELETE"}`.
45. **Search reuses `provider.search`** (semantic with Mem0, word overlap with the Fake). The list is newest first, capped at 100 for now; real pagination arrives if it's needed.

## Stage 7
46. **Custom memory is a second `MemoryProvider`** next to Mem0, chosen by `MEMORY_PROVIDER`. Same interface, separate stores, so Stage 9 can compare them fairly.
47. **Embeddings are their own interface** (`EmbeddingProvider`), not part of the chat LLM: they come from a local model, and the chat vendor can change without touching memory. Fake (offline) and fastembed (real, optional install).
48. **One `memories` table with `vector(384)`**, an `Embedding` type that is pgvector on Postgres and a JSON list on SQLite, so unit tests stay fast while a separate suite exercises real pgvector.
49. **HNSW + cosine** (see docs/memory-system.md for why not IVFFlat, and the per-user filter caveat).
50. **Similarity is a gate; importance/recency/pinned only re-rank.** Weights and half-life are config. The gate threshold is uncalibrated until Stage 9.
51. **Batched extraction with hard validation.** One LLM call and one embedding batch per exchange; unusable model output degrades to "no memories".
52. **Edits re-embed**, so search follows the new meaning of an edited memory.
53. **Only exact (case-insensitive) duplicates are skipped now**, to stop obvious repeats; real semantic dedupe is Stage 8.
54. **Real-Postgres tests are opt-in** (`TEST_POSTGRES_URL`), so everyday runs need no Docker. They run in CI against a pgvector service.
55. **Hard delete** for now (Stage 6 behaviour); `status` exists in the schema for Stage 8's superseded/pending flow.

## Forgot password (added after Stage 7)
56. **It was missing from the original plan, not a bug**: Stage 3 listed "no password reset" as a limitation. Added as its own small piece before Stage 8.
57. **Same answer for known and unknown emails** (202 + identical message), email sent in a background task, and a one-per-minute cooldown per account. Prevents probing which emails are registered.
58. **Single-use, hashed, short-lived tokens** (30 min), consumed atomically; a new request voids older links; a reset revokes all sessions.
59. **Pluggable `EmailSender`**: `console` (default, zero setup, dev only) and `smtp` (stdlib `smtplib`, STARTTLS). No vendor SDK, so $0 and swappable; failures to send are logged, never shown (would reveal the account).
60. **The reset token is removed from the browser URL on load** to limit leaks through history, screenshots and referrers.

## Stage 8
61. **Two-tier de-duplication**: vector similarity decides the clear cases for free; only the ambiguous band costs an LLM call, and all ambiguous pairs of an exchange share one call. Failure defaults to "keep both".
62. **Conflicts supersede, never delete.** The old memory stays, restorable, with history. Restore is a swap, so the user's last explicit choice wins and nothing is lost.
63. **`ask` mode is a real inbox**: pending memories are excluded from retrieval and from duplicate checks against active ones; a pending conflict stores which memory it would replace and applies that only on approval.
64. **Self-referencing foreign keys with `ON DELETE SET NULL`** (`superseded_by`, `supersedes_id`): deleting a memory can't break its neighbours.
65. **Versions are a separate table** (previous text + reason), not a JSON column: queryable, cascades on delete, and it keeps the memory row small.
66. **The sensitive-data guard is code, not just a prompt** (prompts can be ignored). Applied to extracted candidates and manual edits. It blocks rather than redacts, and is documented as best-effort.
67. **One transaction per exchange** for all inserts/merges/supersedes, so a failure midway leaves no half-applied conflict resolution.
68. **Lifecycle features are optional capabilities** on `MemoryProvider` with empty defaults, so Mem0 and the fake provider keep working unchanged and the UI shows the extra tabs only for the custom provider.

## Stages 9-12
69. **Analytics use persisted events, not dashboard guesses.** Each completed reply writes a `usage_events` row and each retrieved memory writes a `memory_retrievals` row. The dashboard aggregates only the authenticated user's rows.
70. **The first focus card is deterministic.** It combines high-importance/pinned goal memories instead of adding another LLM call. This makes the feature useful offline; a cached LLM rewrite can replace it later.
71. **Rate limiting starts process-local.** `InMemoryRateLimiter` gives local Docker and one-instance deployments a clear inexpensive guard. It is deliberately behind one small module so Redis can provide shared counters when replicas are introduced.
72. **Settings are persisted per user.** Global memory state is enforced at turn construction, so a client cannot bypass it by creating a conversation with memory enabled.
73. **Privacy export/delete operates on the authenticated user only.** Account deletion uses database cascades so conversations, messages, memory rows, tokens and telemetry leave together.
74. **The LangGraph workflow is intentionally narrow.** It has two observable nodes—retrieve relevant user facts, then make a study plan—and shares the normal `MemoryProvider`. It is optional at runtime so the rest of the API still starts without LangGraph installed.
75. **Docker's browser API path is reverse proxied through Nginx.** The same `/api` path works in Vite development and the static production container, avoiding CORS-dependent frontend configuration.
